Connecting AI to Odoo for continuous auditing: access, evidence and approvals

The data an auditor needs is already in Odoo every day. The design question is how AI reaches it without becoming a new risk.

OdooBy Ahmed Ashraf Mostafa14 October 20267 min read

Reviewed by MFT audit and Odoo practicelast reviewed 14 October 2026

Short answer

To connect AI to Odoo for continuous auditing, give the analysis layer its own dedicated user with read access only, through the external API or the MCP connection listed in Odoo’s 20 release notes. Keep client data on the client’s system, make every finding cite the record ids it read, and route any proposed correction to a named approver.

Key takeaways

  • The audit connection gets its own user, its own key and read access only.
  • Ask where data is processed and stored before asking what the model can do.
  • A finding without the record ids behind it is an opinion, not evidence.
  • Corrections are drafted by the system and approved by a named person, never posted by the connection.

Picture a familiar year-end conversation: the auditor finds a vendor paid twice in the second quarter, the board asks why nobody noticed, and the honest answer is that the payment sat in Odoo for nine months while everyone waited for the annual audit. We wrote about that gap in why an annual audit misses eleven months. The fix is not more auditors. It is a connection that reads the books every day and raises the question while the money can still be recovered.

Connecting AI to an ERP is easy to demonstrate and easy to get wrong: the connection is a new user that sees everything the auditor sees, often run by a third party, often processing data outside the company. This article sets out the design decisions in the order an auditor would check them.

What does connecting AI to Odoo for continuous auditing mean?

Connecting AI to Odoo for continuous auditing means giving an analysis layer governed, logged and read-only access to the ledger, so that tests run on the full population on a schedule and every result points back to the records it came from. Two words in that definition carry the weight. Governed means someone owns the connection, its rights and its output. Points back means a finding can be reopened in Odoo by anyone who doubts it.

It fits the monitoring component of COSO’s Internal Control, Integrated Framework (2013): Principle 16 calls for ongoing and separate evaluations, and a daily test run is an ongoing evaluation. For how this differs from the annual cycle, see continuous auditing with AI vs traditional auditing.

Why should the audit connection read only?

Because the auditor must not be able to change what the auditor tests. If the connection can write, a finding and its fix can come from the same identity, which breaks the segregation of duties the audit is meant to test. ISA 315 (Revised 2019) asks auditors to understand the IT environment and general IT controls; an audit connection with write rights is exactly the kind of access that understanding should flag.

  1. Create a dedicated user for the connection. Never reuse a person’s login or an administrator account.
  2. Grant read access only to the models the tests need: journal entries, invoices and bills, payments, partners, products and stock valuation.
  3. In Odoo 20, record rules are removed and the domain is set directly on the access right, so review that domain as part of the setup.
  4. Issue an API key for that user alone and record who holds it and when it will be rotated.
  5. Review the user’s chatter monthly: Odoo 20 logs user group changes there, so any widening of rights leaves a trail.
  6. Test the restriction: attempt a write with the key and file the refusal as evidence that read-only holds.

Read-only applies to the connection, not to everything AI does. MFT’s seg-audit platform reads the books straight from the ERP, read-only. Our Auditor agent does more: it drafts correcting entries and adjustments, but drafting is not posting, and nothing reaches the ledger without approval. For segregation of duties when an agent is in the chain, see AI, segregation of duties and internal controls.

Where does the data go, and who keeps it?

Data residency is the question owners ask last and should ask first. A connection that copies the whole ledger to an outside store creates a second set of books, outside your controls and possibly outside your country. Ask every provider, including us, the same questions:

  • Is client data stored by the provider, or read at query time and discarded?
  • In which country is it processed, and by which AI model provider?
  • How long are prompts, answers and logs kept, and can they be deleted on request?
  • Who at the provider can see the data, and is that access logged?
  • Does the provider’s contract match your data-protection obligations, as confirmed by your legal adviser?

Our own answer is that client data stays on the client’s system and our agents read through the API at query time. Odoo’s native AI has its own retention rule: according to the release notes, stored conversations are kept up to 30 days after the last message. Know both rules before anything goes live.

Which tests should run continuously?

Start with tests whose exceptions are cheap to verify and expensive to miss. These are the patterns that recur in our continuous-audit work:

  • Duplicate and near-duplicate payments: same vendor, similar amount and reference, close dates.
  • Near-duplicate vendors: similar names, shared bank accounts or tax numbers.
  • Approvals outside the approval matrix: bills or orders approved above the approver’s limit.
  • Cut-off errors: receipts and bills recorded in different periods around month end.
  • Inventory valuation drift between the stock valuation and the general ledger.
  • Manual journal entries posted late at month end in round amounts, which ISA 240 already requires auditors to test.

Each test reads the whole population, not a sample, which is the subject of moving from sampling to full-population testing. The ACFE’s 2024 Report to the Nations found the median fraud lasted 12 months before detection, and that proactive data monitoring and analysis was among the controls associated with roughly half the losses and duration. A daily test proves nothing alone; it shortens how long a problem stays hidden.

How does an AI finding become audit evidence?

Only by pointing at the records. ISA 500 asks whether evidence is sufficient and appropriate, and ISA 230 asks that documentation let an experienced auditor understand what was done. An AI sentence meets neither. A finding that lists the record ids it retrieved, the rule that flagged them and the time of the query meets both, because anyone can reopen those records in Odoo.

If a finding cannot name the records it read, it is not a finding. It is a rumour with a confidence score.

That is the rule MFT Intelligence runs on, which we call "evidence or silence": every finding must cite the record ids the agent actually retrieved, and a finding that cites nothing, or quotes a number not in the cited records, is rejected and shown struck through, never as fact. The details are in our article on AI provenance and the zero-hallucination principle. The standards are moving too: in August 2026 the IAASB issued exposure drafts revising ISA 500, ISA 330 and ISA 520 to address greater use of technology, with comments due 15 December 2026. They are not final, so build on the current standards.

Who approves what the AI proposes?

A named, registered person, never the connection and never the person who asked for the run. Our rule set, described in agents draft, people approve, is:

  • The agent drafts the correcting entry or adjustment; nothing is posted automatically.
  • Approval is tiered by the client’s ISA 320 materiality threshold: above it, a second approver signs.
  • Corrections are made by reversal, never by deletion, so the original stays visible.
  • In seg-audit, a finding cannot be closed without a named, registered approver, and repeats are linked to earlier findings.

Live Odoo write-back of approved corrections is delivered per client, only after that client’s connector is configured. Until then, approved corrections are entered by the client’s own team, which keeps the posting under their controls.

Where should you start?

  1. Write down the purpose of the connection, its owner and the tests it will run.
  2. Create the dedicated read-only user and key, and test that a write is refused.
  3. Get written answers to the five residency questions above.
  4. Run three tests on a closed quarter first, such as duplicate payments, near-duplicate vendors and late round-amount journal entries, and calibrate false positives.
  5. Agree who reviews exceptions, in what time frame, and who approves corrections.
  6. Review the connection’s log, rights and findings monthly, as you would any privileged user.

This is the work behind our internal audit service: seg-audit reads the books read-only, scores every transaction by risk instead of sampling a few percent, and keeps each finding on record with evidence and severity. Questions people ask

Can AI connect directly to Odoo?

Yes. Recent Odoo versions offer an external API (XML-RPC and JSON-RPC) used with a dedicated API user and key, and Odoo’s 20 release notes add connecting to the database via MCP (Model Context Protocol). Confirm in your own database which user and rights each connection runs under before enabling it.

Should an audit AI have write access to Odoo?

No. The connection used for continuous auditing should read only, so the tool that tests the books cannot change them. If an AI system proposes corrections, they should arrive as drafts approved by a named person, with corrections made by reversal rather than deletion.

Does connecting AI to Odoo move my data outside the company?

It depends on the provider. Some copy the ledger to their own storage; others read through the API at query time. Ask where data is processed, by which model provider, how long prompts and logs are kept, and who can see them, and have your legal adviser check the contract.

Can AI findings be used as audit evidence?

Only when they trace to records. A finding that lists the record ids retrieved, the rule applied and the time of the query can be reopened and verified, which is what ISA 500 and ISA 230 expect. An unsupported AI statement is not evidence, however confident it sounds.

What should continuous auditing test first in Odoo?

Start with tests that are cheap to verify and costly to miss: duplicate and near-duplicate payments, near-duplicate vendors, approvals outside the approval matrix, cut-off errors, inventory valuation drift, and manual journal entries posted late at month end in round amounts. Run them on a closed period first to calibrate.
