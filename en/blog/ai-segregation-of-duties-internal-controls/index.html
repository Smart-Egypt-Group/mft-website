AI and segregation of duties: internal controls when agents are users

An AI agent that can write to the ledger is a new user in your control design. Here is how to place it in the SoD matrix and use AI to test it.

Internal auditBy Ahmed Ashraf Mostafa14 October 20267 min read

Reviewed by MFT audit and Odoo practicelast reviewed 14 October 2026

Short answer

AI changes segregation of duties because an AI agent that can create or update accounting records is, for control purposes, a user. It must sit in the SoD matrix with a role, an owner and minimum rights. Keep its output in draft for a named person to approve, and use AI to test conflicts across every transaction.

Key takeaways

  • An agent that can create or update records performs the recording function and belongs in the SoD matrix.
  • Agents may draft, propose and monitor; authorization and custody stay with named people.
  • AI adds configuration conflicts: the person who writes an agent’s instructions should not approve its drafts.
  • Used as a detective control, AI checks who actually did what on every transaction, not who could have.

Run a user access review on an ERP where AI has been on for a few months and a new kind of line appears. It is not a person, it has no job description, it was set up by IT or the implementation partner, and it can create and update records in Accounting. Nobody put it in the segregation of duties matrix, because the matrix was written for people.

The basics of conflicting duties in Odoo are in our guide to segregation of duties in Odoo. This article asks what changes when some hands in a process are agents, and how the same technology can test segregation on every transaction. It is part of our series on AI in accounting in 2026.

What is segregation of duties when AI is part of the process?

Segregation of duties is the design rule that no single user, human or automated, can authorize, record, hold custody of and reconcile the same transaction. The four functions have not changed; the list of users has. COSO’s Internal Control, Integrated Framework (2013) has a place for this: Principle 10 covers control activities such as segregation, and Principle 11 covers general controls over technology, which is where the configuration of an AI agent belongs. ISA 315 (Revised 2019) requires the external auditor to understand the IT environment and general IT controls, so an agent with write access will be in scope at your next audit whether you mapped it or not.

Is an AI agent a "user" for segregation of duties?

For control purposes, yes: the test is whether the actor can change the books. According to Odoo’s 20 release notes, AI agents can create records (including from an uploaded instruction file such as a PDF), update records, and be triggered by automated actions and scheduled actions. Anything that can create or update an accounting record performs the recording function and must sit in the matrix with a role, an owner and limits.

Before designing anything, confirm in your own Odoo 20 database under whose access rights an agent’s actions run and how its changes are attributed in the record history; that decides whether a conflict sits with the agent, the person who triggered it, or both. Also confirm which AI features your edition and plan include. Every AI request consumes IAP credits, billed per request and not included in any plan.

Decision rule: which of the four functions may an agent hold?

Which conflicts does AI introduce that a classic SoD matrix misses?

AI adds conflicting pairs that sit in configuration, not in transactions, so a classic matrix misses them:

  • Agent configurer and approver. Whoever writes an agent’s instructions and skills shapes every entry it drafts. In Odoo 20, "topics" are renamed "skills" and default prompts accept context and dynamic values, so a one-line change can alter a month of drafts. That person should not approve them.
  • Requester and approver of the same run. The person who asks an agent to prepare a correcting entry should not be the one who approves it.
  • Trigger owner and process owner. Agents can be fired by automated and scheduled actions, and Studio automation rules can now trigger activity plans. Changing a trigger is changing a control, so it needs change management.
  • Button clicker and authority holder. Odoo 20 agents ask questions, request permission and make suggestions answered by buttons, and they ask before exceeding their tool call limit. Each click is an approval, so define who may click.
  • Connection owner and data owner. The release notes describe connecting to the database via MCP. An external connection is a user with rights; it belongs in the matrix and in your design for connecting AI to Odoo.

How do you design internal controls for AI agents in Odoo?

Treat each agent like a new team member who works fast, never tires and has no judgment. Our procedure:

  1. Inventory every agent, every automated or scheduled action that calls AI, and every API or MCP connection. Record its owner, its trigger and the models it can create or update.
  2. Map each one to the four functions and add it to the SoD matrix as its own row, next to the people.
  3. Set its access rights to the minimum. Odoo’s 20 release notes say record rules are removed and the domain is set directly on the access right, so any restriction you relied on before an upgrade must be re-checked, not assumed.
  4. Keep agent output in draft. A named person who did not configure the agent posts it. Confirm in your database that the agent’s rights do not allow posting or confirming.
  5. Tier approvals by materiality: above your ISA 320 materiality threshold, require a second approver.
  6. Correct by reversal, never by deletion, and protect closed periods with lock dates (long-standing in recent Odoo versions; confirm in your 20 database who can change them).
  7. Retain evidence outside the chat. Stored AI conversations are kept up to 30 days after the last message, so anything you need as audit evidence must be captured in the record or a working paper before then.
  8. Review agent rights and configuration every quarter, using the user group change log that Odoo 20 keeps in each user’s chatter.

The governance of the agents themselves is covered in Odoo 20 AI agents under finance controls, and the principle behind step 4 is set out in agents draft, people approve.

An agent that can write to the ledger is a user. Give it a role, an owner, and a person who signs for its work.

How can AI test segregation of duties instead of threatening it?

A manual access review checks who could act. A data test checks who did act, on every transaction. The difference matters: the ACFE’s Occupational Fraud 2026 report found that more than half of cases involved a lack of internal controls or an override of existing ones, and that proactive data monitoring is associated with lower losses and faster detection.

Running these tests on every record is the subject of full-population testing with AI. A hit is a lead, not a finding: two conflicting roles held by one user is a design weakness, and whether it was exploited is a question for evidence, as explained in AI-based fraud detection.

What if the team is too small to separate duties?

A two-person team cannot split seven conflicting pairs, and agents do not change that, because an agent cannot carry accountability. The answer is still compensating controls, now cheaper to run. An owner or general manager outside the transaction reviews a short monthly exception list produced by AI: users who both created and approved, vendor bank changes followed by payments, manual entries after the close. The review is quick because the list is short, and documented because the list is a record. That is COSO Principle 16 (ongoing and separate evaluations) in a form a small team can sustain.

Where to start on Monday

  1. List every AI agent, automation and external connection in your ERP, with one named owner for each.
  2. Add them as rows in your SoD matrix and mark the function each one performs.
  3. Remove posting, confirming and payment rights from agents; keep them on draft.
  4. Run one detective test on the last quarter: users who both created and approved the same journal entry or vendor payment.
  5. Agree who reviews the exceptions, and how evidence is kept beyond the 30-day conversation window.

Questions people ask

Can an AI agent approve transactions in an ERP?

It should not. Approval carries accountability, and an agent cannot be held accountable. Let the agent prepare the approval file, such as the supporting records and the exceptions it found, and leave the decision to a named, registered person. Above your materiality threshold, add a second approver who did not request the agent’s work.

Who should configure AI agents in the finance system?

Someone who does not approve what the agent produces. Writing an agent’s instructions shapes every draft it creates, so it is a recording function. Separate it from approval, put configuration changes under change management, and review the configuration history at least quarterly alongside user access rights.

How does AI help test segregation of duties?

It reads every transaction instead of a sample and checks who actually acted: the same user creating and posting a journal entry, changing a vendor’s bank details and releasing a payment, or approving outside the approval matrix. Each hit is a lead for review, documented with record ids, not a confirmed violation.

Does Odoo 20 change access rights for segregation of duties?

According to Odoo’s 20 release notes, record rules are removed and the domain is set directly on the access right, and user group changes are logged in the user’s chatter. After upgrading, re-test every restriction your segregation design relied on and use the change log as review evidence.

Is a segregation of duties conflict found by AI proof of fraud?

No. A conflict shows that one user could, or did, perform two functions that should be separate. That is a control weakness. Whether anyone misused it is a separate question answered by examining the underlying transactions and documents, with the person involved given a chance to explain.
